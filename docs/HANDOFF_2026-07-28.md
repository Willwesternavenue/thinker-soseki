## 2. ⚠️ 最重要の運用注意（このセッションで実際に踏んだ罠）

0. **破壊的テストは既定で skip される。skip は安全装置であって免除ではない**
   （2026-07-30 追加）。`clean_corpus` を使う**13ファイル**は、接続先が本物の
   コーパスに見えると skip する。何もしなければこの13ファイルは**恒久的に
   走らない回帰の穴**になるので、走らせる時機を運用として決めてある。

   | いつ | 何を |
   |---|---|
   | **main へマージする前（通過条件）** | 破壊系を含めて全件通す。ここを飛ばさない |
   | コーパス層（`aozora/` `creative/`）を触ったとき | その領域だけでも通す |
   | プロンプト・文言だけの変更 | 既定の skip のままでよい |

   走らせ方は2つ。**第一分岐を常用経路にすること**:
   ```bash
   # ① 専用スタック（本筋。開発DBに触れないので退避も要らない）
   SUPABASE_TEST_URL=... SUPABASE_TEST_SECRET=... uv run pytest
   # ② 逃げ道（最後の網。直前に退避を取ったと分かっている場合のみ）
   SOSEKI_ALLOW_DESTRUCTIVE_TESTS=1 uv run pytest
   ```
   ②の行数ヒューリスティック（`source_chunks` が500行超なら止める）は最後の網で
   あって常用するものではない。**次の区切りで `SUPABASE_TEST_URL` 用のスタックを
   立て、①を既定にすること**（未着手）。

1. **worker の `uv run pytest` はローカルDBを全消しする**（`clean_corpus` fixture）。
   上の安全装置を迂回した場合はこれが起きる。実行前に必ず退避すること。
   退避・復元（ホストの pg_dump はバージョン不一致で使えない。docker 経由で）:
   ```bash
   # 退避
   docker exec supabase_db_thinker-soseki pg_dump -U postgres -d postgres \
     --data-only --no-owner \
     -t canonical_works -t work_editions -t aozora_manifest_entries \
     -t canonical_work_review_queue -t sources -t source_chunks \
     -t thought_cards -t thought_evidence_links -t thought_questions \
     -t judgment_rules -t judgment_rule_versions -t judgment_rule_evidence \
     -t creative_profiles -t creative_cards \
     -t creative_generations -t creative_traces \
     > backups/phase_c_data_$(date +%F).sql
   # 復元
   docker exec -i supabase_db_thinker-soseki psql -U postgres -d postgres -q \
     -v ON_ERROR_STOP=1 --single-transaction \
     -c "set session_replication_role = replica;" -f - < backups/<最新の退避>.sql
   ```
   復元後は必ず行数を突き合わせる（直前に確認した値と比較する。参考値は
   2026-07-30 時点で `source_chunks` 10,152 / `thought_cards` 57 /
   `judgment_rules` 29）。
   ⚠️ **退避対象は `clean_corpus` が消すテーブルと必ず一致させること**。
   2026-07-30 まで `creative_generations` / `creative_traces` が退避から漏れており

   テーブルを増やしたら conftest と両方を直す。
   ⚠️ **「最新の退避」は日付でなく `backups/` を実際に見て決めること**。
   ファイル名は `phase_c_data_YYYY-MM-DD.sql` の日付順とは限らない
   （同日中に複数回取ることがある）。`ls -t backups/*.sql | head -1` で

**バグ1: 留保（abstention）が思想質問で発火しない**

`MIN_DIRECT_SOURCE_SCORE = 0.45`（`corpus-routing.ts`）はコサイン類似度用に較正した
閾値。§12.3 に「開化0.68 / 生成AI0.35 / 暗号資産0.24、その間に置いた」と根拠がある。
ところが承認リンク由来は最小0.6、全文検索は0.5で、**質問との関連度に関係なく必ず
閾値を超える**。承認リンクが1件でもあれば `hasDirectSource` が常に true になる。

実データで再現（`answer_traces` の実チャット記録）:
```
user_query        : スマートフォンについてどうおもいますか
query_kind        : thought
direct_source_ids : {AOZORA_000788}   ← 『中味と形式』
abstention_reason : (NULL)            ← 発火していない
```

⚠️ **見逃された理由が §12.3「既知の制約」に書いてある** — 「上表の検証は
`fact` / `person_or_work` に分類される聞き方で行った」。`fact` ルートは
`thoughtIds` が空で `fetchLinkedEvidence` を通らない。**2026-07-28 にカード12枚を
承認しフォールバックを設定した時点で、コードを一行も変えずに留保が死んだ。**

**バグ2:「小説を後ろへ下げる」防御が選抜に効いていない**

`pipeline.ts`:
```ts
const evidence = rankByRoute(
  diversifyEvidence(mergeEvidence(linked, routed, unscoped)),  // ← 先に10件へ切る
  routeKind
);
```
`diversifyEvidence` が先に `MAX_EVIDENCE = 10` へ切り詰めるため、`rankByRoute` は
「既に選ばれた10件の並べ替え」しかできず、**何を残すかには影響しない**。
作者直接発言は全10,152チャンク中408件（4%）しかない。

実測で最悪ケースを再現済み（小説寄りの検索語で `match_source_chunks_all`）:
```
narrator / narrative_reference | 10 件   ← 上位10件が全て小説
```
この状態だと `hasDirectSource` が false になり、**原典があるのに留保が出る**。

`rankByRoute(...)` → `diversifyEvidence(...)` の順にすれば直る可能性が高いが、
`diversifyEvidence` はスコア順ソートを前提にしているので、順序を変えると多様性制御の
挙動も変わる。実装を読んでから決めること。

  thought_eligibility。§12.2 で1層ずつ壊して検証済み）
- LLM 出力は自動で approved にしない。承認の関門は迂回不可
  （カード→規則→ブリッジの鎖。読み出し時にも再検証）
- 思想がチャット創作依頼に入る唯一の経路は承認済みブリッジ（§12.7）
- 人手レビューの結論（reviewed/corrected）を LLM の再実行で上書きしない
- 帰属（誰の発言か）は本文と同じ場所に明示し、trace に残す
