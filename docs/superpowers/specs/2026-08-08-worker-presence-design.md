# ワーカー不在の可視化と起動（設計）

2026-08-08 / 対象: `/creative`（創作）と `/admin/jobs`（取り込み）

## 1. 解こうとしている問題

創作を依頼したのに画面が「準備中 0/8」から動かない。実際にはワーカーが
起動していなかった。

```
job 0572deff : status=pending / current_step=空 / 作成から3分間 更新なし
worker_heartbeats.last_seen_at : 6日前
```

画面は `current_step` を正しく映しているだけで、間違ってはいない。問題は
**「登録されたが誰も拾っていない」と「拾われて処理中」が同じ表示になる**こと。
エラーも警告も出ないため、利用者はターミナルを見るまで原因に辿り着けない。

これは引き継ぎ §2 3-b の「静かな劣化」と同じ構造である。安全装置や実行者が
黙って不在になっても、画面上は正常に見える。

本番構成（frontend はクラウド、worker は手元の Mac）では、ワーカーの起動忘れは
**いまより起きやすくなる**。

## 2. 前提となる決定（合意済み）

| 論点 | 決定 | 理由 |
|---|---|---|
| 本番での起動ボタン | **ローカル かつ 管理者のときだけ描画する**（`canStart && isAdmin`） | クラウドの frontend から手元のプロセスは起こせない。押しても効かないボタンを出さない。⚠️ 権限条件は当初この表に無く、実装レビューで足した — `/creative` はログインのみでロール不問（`page.tsx`）なので、ローカル判定だけでは tester に押せるボタンが出る。`startWorker()` は `requireAdmin()` で**例外**を投げるため、押すと理由も出ないまま固着した |
| 起動コマンドの表示 | **管理者のときだけ** | 実行できない相手にターミナルコマンドを見せない。ボタンと同じ理由 |
| 表示範囲 | **共通部品にして創作＋取り込みの両方** | `worker_heartbeats` は `ingestion` の1行だけで、同じプロセスが両方のジョブを処理する。片方だけ直しても同じ問題が残る |
| 検知の粒度 | **不在＋順番待ちを区別する** | `current_job_id` を見るだけで済み、「準備中のまま動かない」の原因が画面だけで分かる |
| 二重起動の防止 | **案A（画面側でハートビートを確認してから起動）** | §5.2 に残余リスクを明記 |

## 3. 部品と責務

境界は「DBに触るか」「プロセスを起こすか」で切る。

| 部品 | 置き場所 | 責務 | 依存 |
|---|---|---|---|
| `workerPresence()` / `workerStatusView()` / `workerStartOutcome()` / `nextStartWatch()` | `frontend/src/lib/worker-presence.ts` | 生死判定・**表示の分岐**・起動の見張りを返す純関数 | なし |
| `getWorkerHeartbeat()` | `frontend/src/app/creative/actions.ts` | `worker_heartbeats` を1行読む server action | Supabase |
| `<WorkerStatus>` | `frontend/src/components/worker-status.tsx` | `workerStatusView()` の結果を描くだけ | 上2つ |
| `startWorker()` | `frontend/src/lib/worker-control.ts` | ローカル限定でプロセスを起こす server action | `child_process` |

判定を純関数として独立させることで、**DBもプロセスも無しで全状態を検証できる**。

表示の分岐も純関数へ出す。既存のテスト11ファイルはすべて `.test.ts` で TSX
テストの前例が無く、分岐をコンポーネント内に置くと検証が前例作りとセットに
なるため。コンポーネントは描くだけの部品にする。

`getWorkerHeartbeat()` は創作画面の既存 server action 群に置く。共通化は
`/admin/jobs` を触らない判断（§2）と釣り合わない。

## 4. 状態判定

`HEARTBEAT_INTERVAL_SEC = 10`（`worker/src/main.py`）なので、不在の閾値は
**30秒（3周期）**とする。1周期では書き込み遅延で誤検知し、長すぎると気づくのが
遅れる。

| 条件 | 状態 | 画面 |
|---|---|---|
| `last_seen_at` が無い、または30秒より古い | `absent` | 警告＋起動UI（文言は待っているジョブの有無で変わる。§4.1） |
| 生存 かつ `current_job_id` が自分 | `running` | 通常の進捗 |
| 生存 かつ `current_job_id` が他 | `queued` | 「他の**処理**を実行中です」 |
| 生存 かつ `current_job_id` が null | `idle` | 表示なし |

`queued` を「他の**生成**」と書かないこと。`worker/src/main.py` のとおり同一
プロセスが `ingestion_jobs` / `distillation_jobs` も回すため、取り込み中にも
この状態になる。

### 4.1 `absent` の文言は2通り

待っているジョブがあるかで変える。無いのに「依頼は保存されていますが」と
書くと**嘘になる**。画面を開いただけの利用者が最も多く通る経路なので、
ここを取り違えると誤情報がいちばん頻繁に出る。

| 待っているジョブ | 文言の向き |
|---|---|
| あり | 「依頼は保存されていますが、処理する Worker が起動していないため始まりません」 |
| なし | 「いま依頼しても始まりません」 |

そのため `workerStatusView()` は生死だけでは決まらない。引数は
`(presence, { canStart, isAdmin, hasPendingJob })`。**表示は「ワーカーの状態」
だけでなく「誰が見ているか」「何を待っているか」の関数である。**

「自分の job_id」は呼び出し側が渡す。`/admin/jobs` のように**特定のジョブを
待っていない画面では渡さない**。その場合 `running` / `queued` は区別せず、
生存していれば `idle` 扱い（表示なし）とする。不在の警告だけが要るためである。

⚠️ **判定は `status` 列ではなく `last_seen_at` の古さで行う。**
ワーカーが落ちても行は最後の値のまま残る。実際、調査時の
`worker_heartbeats` には6日前の `status: processing` が残っていた。
`status` を信じると死んだワーカーを生きていると誤認する。

## 5. 起動

### 5.1 手順

```
1. SUPABASE_URL のホストが localhost / 127.0.0.1 か  → 違えばボタンを描画しない
2. requireAdmin()
3. ハートビートを再確認（押す直前に誰かが起動していたら何もしない）
4. spawn("uv", ["run","python","-m","src.main"],
         { cwd: <repo>/worker, detached: true, stdio: "ignore" }).unref()
5. 画面はポーリングを続け、ハートビートが現れたら警告が自然に消える
```

ローカル判定に `SUPABASE_URL` を使うのは、「これから起動するワーカーが、いま
画面が見ているDBと同じDBを見るか」と条件が一致するため。`NODE_ENV` では
本番ビルドをローカルで動かしたときにずれる。

### 5.2 残余リスク（案Aを選んだ結果として残す）

`claim_next_generation` は**非排他**である。コード自身がそう宣言している:

```python
"""pendingの創作生成ジョブを1件処理する。
claimは既存ジョブと同じく非排他(単一worker前提)。"""
```

手順3の確認から、起動したプロセスが最初のハートビートを書くまで**最大10秒**の
窓がある。この間に連打すると2つ起動し、同じジョブを二重処理する。

緩和として、押した直後にボタンを無効化して「起動中…」を出す。**いつ戻すかが
効き目を決める。** `startWorker()` の返却で戻すと spawn 直後（数百ms）に有効化
され、窓の内側で連打できてしまう。そこで**ハートビートが出るか、30秒
（`WORKER_ALIVE_THRESHOLD_SEC`）を過ぎるまで**無効のままにする。窓の長さと
不在判定の閾値が同じ値なのは偶然ではなく、「起動が効いたと分かるまで」と
「落ちていると判断するまで」が同じ観測に依るためである。

これは事故を**減らすが塞がない**（別タブから押せば同じことが起きる）。

塞ぐには worker 側で Postgres の advisory lock を取り、取れなければ即終了する
必要がある（起動経路を問わず効くため、ターミナルからの二重起動も防げる）。
今回は採らない。**採らなかったという判断をここに記録しておく。**

## 6. エラー処理

| 事象 | 挙動 |
|---|---|
| ハートビート取得が `error` を返す | 警告を出さない（フェイルオープン） |
| **ハートビート取得が例外で落ちる**（`requireUser()` の失効、POST 自体の失敗、オフライン） | 同上。**ただし時計だけは進める** |
| `uv` が見つからない等で spawn 失敗 | 起動から30秒でハートビートが出ないことで検知し、コマンドを提示 |
| 起動したがハートビートが出ない | 30秒待って「起動できませんでした」に変え、コマンドを提示 |
| 起動が成功し、その後ワーカーが落ちた | **「起動できませんでした」を出さない。** 見張りはハートビート到着時に解除する |

⚠️ **取得失敗を「不在」と扱わない。** 誤警告が続くと警告そのものが無視される
ようになり、いま直したばかりの「静かな劣化」を人間側で再現することになる。

⚠️ **例外で落ちた回も時計は進めること（実装で最も見落としやすい）。**
経過時間の更新を取得成功の経路にだけ置くと、取得が失敗し続けている間
`now` が凍り、`ageSec` が増えなくなる。結果、**その間に落ちたワーカーを
永久に不在と判定できない**。フェイルオープンは「警告を出さない」であって
「時間を止める」ではない。

⚠️ **catch を無言にしないこと。** 痕跡が残らないと、警告ボックスが理由なく
消え続ける状態になる。これは §1 で問題にした形そのものである。

## 7. テスト

- **純関数 `workerPresence()`** — 4状態、境界（29秒 / 31秒）、`last_seen_at` が
  null。ここが主戦場
- **純関数 `workerStatusView()`** — 権限・待機ジョブの有無で文言と表示要素が変わること
- **純関数 `workerStartOutcome()` / `nextStartWatch()`** — 起動の見張り。
  **「起動成功の数分後にワーカーが落ちた」時系列を必ず含めること。**
  この状態遷移は設計時に想定されておらず、実装時は JSX 内に埋もれて
  テストから到達できず、そこだけにバグが残った
- **`startWorker()`** — 接続先が非ローカルなら起動しない／生存中なら起動しない／
  取得が失敗したら起動しない／**管理者でなければ例外になる**。
  `child_process` を差し替えて確認し、`detached` と `cwd` も検証する
  （コマンド名だけ見ると、消しても緑のままになる）
- **`<WorkerStatus>`** — 分岐を持たないため独自テストは置かない

実プロセスの起動そのものは自動テストしない（副作用が大きく、CI で意味を
持たない）。代わりに手動確認の手順を §8 に置く。

## 8. 手動確認の手順

1. ワーカーを止め、**管理者で** `/creative` を開く → 30秒以内に不在の警告と
   起動ボタンが出る。**まだ何も依頼していないので、文言は「いま依頼しても
   始まりません」側**であること（「依頼は保存されていますが」なら誤り）
2. ボタンを押す → 押した直後から**30秒間はボタンが無効のまま**であること
   （spawn 直後に再有効化されると連打で二重起動できてしまう）。
   10〜20秒で警告が消える。`worker_heartbeats.last_seen_at` が現在時刻で
   更新されている
3. **手順2の成功後にワーカーを手で止める** → 警告は再び出るが、文言は
   「起動できませんでした」**ではない**こと（起動は成功していたため）
4. 創作を依頼し、別タブでもう一度 `/creative` を開く → 2つ目のタブは
   `queued`（他の処理を実行中）と表示される
5. **tester ロールで** `/creative` を開く（ローカル接続のまま）→ 警告は出るが
   **起動ボタンもターミナルコマンドも出ない**こと
6. `SUPABASE_URL` をクラウドに向けて起動 → 警告は出るが**ボタンは出ない**

## 9. 対象外

- worker 側の排他制御（§5.2）。案Aを選んだ時点での意図的な除外
- 「生きているが同じ step のまま進まない」停滞の検知。LLM タイムアウト
  （120秒）導入後は窓が狭く、誤検知が増えやすい
- クラウドからのワーカー起動。Cloud Run 常駐に戻す判断とセットになるため
