# 創作パイプラインの設計（続編生成の多層防御）

2026-08-01 作成。夢十夜の続編生成で到達した構成と、その判断の理由を残す。
**次の作家・次の作品へ横展開するとき、最初に読む文書**。ここに書いてあるのは
夢十夜固有の事情ではなく、原作を持つ創作生成に共通する構造の話。

## 1. 解こうとしている問題

原作を持つ作家の「続編」を書かせると、出力が原作のメドレーになる。実測では
第一夜の「赤い日を数えて数えきれなくなる」と第三夜の「全知の子供」が
**n=7 で毎回**再現した。原因は単一ではなく、少なくとも4つの経路があった。

1. 章ごとに蒸留した創作カードが、章固有の装置を指示として運ぶ
2. Bridge Rule が、対応先カードの題と要約をそのままプロンプトへ運ぶ
3. 誤分類されたカード（批評カードの棚に置かれた創作指示）が検査をすり抜ける
4. **「原作の続編」という課題設定そのものが、最も有名な章へ滑る**

文字列類似の Guard ではどれも捕まらない。筋・装置のレベルの再現だから。

## 2. 多層防御の分担

| 層 | 役目 | 実装 |
|---|---|---|
| 装置除外 | **汚染源の遮断**。装置を運ぶカード・橋をプロンプトへ入れない | `card_devices.py` / `bridges.py` |
| 前提3案 | **アトラクタの除去**。装置の出現率そのものを下げる | `premises.py` |
| 検出 | **監視記録**。混入の有無を残す（ゲートしない） | `device_catalog.detect_devices` |

重心は**前提レベル**にある。1〜3の経路を全部塞いでもなお 3本中2本が第一夜へ
落ちた（final3）が、前提を固定した途端に 3/3 で消えた（final6）。除外と検出は
フィルタであって、アトラクタの除去ではない。**フィルタをいくら固くしても、
生成側が収束し続ける限り作り直しコストと安全側失敗が積み上がるだけ**。

装置カタログ（`device_catalogs/{source_id}.json`）は3つの用途を1本で兼ねる:
カード判定の照合対象 / 検出の比較対象 / 前提照合の負例集合。一本作って
使い回すという最初の設計判断は、この3用途で回収された。

## 3. 判定基準（現行版）

acceptance は同一 brief で3本走らせ、**3本すべて**で以下を満たすこと。

| | 条件 |
|---|---|
| (a) | **中心前提が装置（またはその2成分以上の骨格）でないこと** |
| (b) | 全知の子供（第三夜の中心装置）の再現がないこと |
| (c) | 種明かし文がないこと（謎を解いて閉じない） |
| (d) | 冒頭定型句「こんな夢を見た」があること |
| (e) | Guard 通過 |
| (f) | **3本が相互に類似していないこと** |

### 改定の理由

**(a) は当初「計数装置なし」だった。** 装置の成分が一場面の所作として残響する
程度（数える描写が一箇所ある等）まで違反にすると、正当な描写まで落とすことに
なる。実際に問題だったのは計数の存在ではなく、**石段+計数が話の骨格だった**
こと。骨格かどうかは成分マッチでは判定できないが、前提レベルなら直接問える。
これに伴い、判定の重心が検出層から前提判定へ移った。

**(f) は前提3案の導入時に新設した。** 装置除外は原作への収束を防ぐが、生成間の
収束は防げない。実測で、装置を抜いた3本が「橋・子供・幼時の顔」で相互に酷似
した。これは除外では原理的に達成できず、過去の採用前提を負例として見せることで
しか防げない。(f) は前提3案の固有の検証項目。

**outline 段の検出はゲートから監視へ降ろした。** 前提が装置でないことを採用
時点で確認済みなら、outline 段で同じ判定をかけるのは二重チェックであり、実測
では偽陽性が正常な生成を殺す側に働いた — 影が体から離れる outline を第七夜
「船からの投身と着水前後悔」と判定して3試行を焼き切った（装置の成分は1つも
一致していない）。第十夜「無限反復による消耗」と第七夜は汚染下でも偽陽性の
常連で、**抽象度の高い共通点（不可逆な離別・反復による消耗）で反応する癖**が
ある。ゲートを戻すなら、成分一致の要求を厳しくして偽陽性率を測ってから。

## 4. 設計原理（横展開時に効くもの）

### 4.1 同時比較で多重比較を消す

判定対象がN個あるとき、N回の独立した二値判定に割ってはならない。1回あたりの
偽陽性率が試行回数で膨らむ。実測: カード16枚×装置10件の総当たりで 11/16 が
除外され、夢十夜由来ですらない批評カードまで第一夜の計数に収束すると判定された。
**多重比較の解消は「試行を1回にする」ことからではなく、判定を独立でなく
同時比較にすることから来る。**

⚠️ ただし**出力の基数**を取り違えないこと。カードは単一のアトラクタへ収束
するので単一強制選択が正しい。テキストは複数の装置を同時に含みうるので複数可の
列挙にする。逆にすると、どちらかが偽陰性側へ壊れる。

### 4.2 精度は機械検証、再現率は judge

judge に「迷ったら挙げるな」と書くと事前確率が歪む。実測: 件数抑制の一文を
入れた版では、実在する装置が3本中1本でしか発火しなかった。judge には
「該当するものは全て挙げよ、根拠を引用せよ」と言い、**精度は引用の機械検証**
（引用が検査対象に実在するかの照合）で守る。幻覚した検出はコード側で破棄できる。

判断根拠を書かせることには副次効果もある: judge を疑って人手で監査したとき、
judge ではなく**人手の正解ラベルの方が間違っていた**と分かることがある
（§6 の A/B で、陰性と決めつけていた1件が実は正当な検出だった）。根拠が
無ければ「judge の誤り」で片付けて終わっていた。

### 4.3 運転点はコストの非対称性で決める

装置検査の場合:
- 偽陽性の代償 = outline 作り直し1回（約 $0.07）
- 偽陰性の代償 = 違反作品の出荷

ガードとしては再現率側へ倒すのが正しい。検出系 judge を設計するときは、まず
この非対称性から運転点を決める。ただし**ゲートするかどうかは別の判断**で、
偽陽性が正常な生成を殺すなら監視へ降ろす（§3 の改定）。

### 4.4 除外は合流点で強制する

除外をカード取得の一箇所でしか効かせないと、プロンプトへ合流する他の経路が
独立にコンテンツを運ぶ。実測: 除外した計数カードの要約が Bridge 経由で復活
していた。個別の経路を塞ぐだけでは次の経路が増えたときに同じ穴が開くので、
プロンプト組み立ての最終段で `assert_exclusions_hold` を実行する。
**プロンプトへ材料を運ぶ経路を増やしたら、ここに追加すること。**

### 4.5 エントロピーはランダム抽選で入れる

前提3案から judge に最良を選ばせない。「judge が好む前提」という新しい
アトラクタができ、生成間の酷似が判定器の趣味の形で再来する。通過案からの
**ランダム抽選**でエントロピー源を確保する。

### 4.6 誤分類されたカードは無関係なカードより危険

レビュアー（人間もLLMも）は種別ラベルを信じて読み飛ばすので、間違った棚に
置かれた創作指示は検査をすり抜けて注入だけされる。実測: criticism カードに
紛れていた「創作を『掘り出す』行為として語らせる」（第六夜の運慶）が、
本文に出典を名指しさせた張本人だった。

否定形・欠如形の指示（「〜しない」「〜を与えない」）は、従っても像を生成
しないので装置を運べない。装置判定の対象外とし、prohibition 側の検査系統へ
回す。同じカードが「生成時の注入では使わないが検査では使う」二役を持てる。

## 5. 実測の要点

| 段階 | 結果 |
|---|---|
| 対策前（n=7） | 第一夜の計数 7/7、第三夜の子供 7/7 |
| カード除外のみ（n=3） | 種明かし 0/3、子供 0/3。計数は 3/3 で残存 |
| 除外+橋封鎖（n=3） | 1本が全条件通過、1本が計数、1本が安全側失敗 |
| **前提3案（n=3）** | **3/3 で全6条件通過。計数の検出ゼロ** |

コスト: 通常1本あたり $0.12〜0.15。カタログ生成・カード判定は一度きりの初期費用。

## 6. 検出モデルの選定（2026-08-01 の A/B・解決済み）

Haiku降格 + union多様化を検討したが、**どちらも採用しなかった**。判断は
実測データに基づく。

**A/B の設定**: 人手で正解ラベルを付けた outline 6本（陽性3・陰性3。ラベル付け
時に1件を誤って陰性と判定し、後で訂正した — 経緯は下記）に、
`detect_devices(model=Sonnet, repeats=3)` と `model=Haiku, repeats=3` の両方を
かけて比較。

| ケース | 正解 | Sonnet | Haiku |
|---|---|---|---|
| 計数あり×3 | 陽性 | 3/3 検出 | 3/3 検出（うち1件は主要装置を外し別章を検出） |
| 陰性×3 | 陰性 | **2/3 正解**（1件は下記の理由で正当な検出） | **0/3 正解** |

速度は Haiku が3〜7倍速い（13〜17秒 対 34〜105秒／repeats=3合計）が、精度の
落差がそれを上回った。

**ラベル訂正の経緯**: 陰性としていた1件（追いつこうとしても距離が縮まらない
outline）を Sonnet は第七夜「追いついても追いつかない太陽」として検出した。
これは outline を読み直すと**正当な検出**だった — acceptance の5条件判定は
この装置を個別に見ておらず、当時見落としていた。Haiku は同じケースで
第七夜に加え第十夜まで検出しており、的を絞った指摘というより広く当てにいく
挙動に見える。これは Sonnet の判断の質を裏付ける材料であり、判断根拠を人手で
監査できるという 4.2 節の設計原理がここでも効いた（Sonnet の誤りだと思っていた
ものが実は自分のラベル付けの誤りだった）。

**union多様化を見送った理由**: 多様化の狙いは「同一モデルの反復は相関するので
見逃しを混合で減らす」ことだったが、今回の3陽性はいずれも Sonnet×repeats=3の
union で取りこぼしゼロだった。混合すべき見逃しの実例が無い一方、Haiku を
混ぜれば union は OR 演算なので陰性側の精度を確実に落とす。

**前提が変わっていたことも一因**: Haiku降格の動機だった46分ハングは、当時
outline 検査が**ゲート**（作り直しを最大3回誘発）だったために深刻だった。
現在は監視モードに降格済み（§3）、かつ呼び出し単位のタイムアウトも入っている
（LLM_TIMEOUT_SECONDS）ため、レイテンシ問題は既に別の2つの変更で解消済み。
Haiku降格が解決すべき問題自体が縮小していた。

**確定した恒久値**: 検出モデルは Sonnet のまま、`DETECT_REPEATS = 3`
（`SOSEKI_DETECT_REPEATS` で上書き可・較正用の逃げ道として残す）。

## 7. 未解決（開いている問題）

**n=3 である。** final6 の 3/3 通過は3本の観測にすぎない。以下は仮説の域を
出ていない。

- **(f) の測定条件が甘い。** 相互類似なしは前提照合リストがほぼ空の状態で
  得られた。リストが数十件に育ったとき、前提生成が「照合リストを避ける」制約で
  痩せていかないか（奇妙さの空間は有限）は未知
- **監視モードの本文検出 1〜2件/本を「偽陽性主体」と読んでいるが、これは仮説。**
  却下 outline の精査では偽陽性と判断できたが、本文側は未検証
- **検出層の見逃し率。** 実在する装置の単発発火率は入力によって 8/10 から 2/5 まで
  振れる。§6 の A/B は union（repeats=3）単位の比較で、単発の見逃し率そのものは
  未解決のまま（k=3 の和集合で 0.8% まで下がる計算だが、相関誤差は解消しない）

これらは今後の final が自然に答えを出すので、先回りの対処は不要。ただし
**閉じた問題と開いている問題を混ぜないこと。**

## 8. 自由創作での対照実験（2026-08-08）

§1〜§7 は**続編**（『夢十夜』第十一夜）を対象にした設計である。本節は
**自由創作**（続編指定なしの依頼）で同じ問題が起きるかを、同一 brief の
対照で測った記録。結論から言うと**起きる**。

### 8.1 きっかけ — 防御が全部 off で回っていた

依頼 `motif: 寺の鐘 / situation: 鐘がなるたび何かが変わる` で生成した作品に
「原作のメドレー」という指摘が出た。記録を確認すると、防御が一つも動いて
いなかった。

```json
"device_check":      {"passed": null},   // 装置検出が走っていない
"body_device_check": {"observed": false},
"fired_rule_ids":    []                  // ブリッジも不発
```

原因は2つで、性質が違う。

1. **`device_exclusion` 未設定（既定 off）** — これは設計どおり。
   `device_exclusion_enabled()` は「続編では汚染源、自由創作では素材」という
   判断で off を既定にしている（§4 の思想ではなくタスク条件付きの制御）
2. **`rules: "off"`** — これは事故。管理画面で Guard 閾値を直しただけで
   `assist` から戻っていた。`buildProfileRow` が
   `default_generation_settings` をフォームの値だけで組み直し、
   `update` が JSON を丸ごと置き換えていたため、入力欄の無いキーが保存の
   たびに消えていた。エラーは出ない（修正済み: `557e651`）

**設定はデータなので、コードのテストでは守れない。** 装置除外を on にしても
同じ経路で消える。§8.4 参照。

### 8.2 対照 — ブリッジだけを戻して同一 brief で再生成

`rules` を `assist` に戻し、`device_exclusion` は off のまま同じ brief を引いた。
`device_check` が両方とも `passed: null` であることを確認しており、**動いた変数は
ブリッジだけ**である。

| 指標 | baseline（`rules: off`） | 対照（`rules: assist`） |
|---|---|---|
| ブリッジ発火 | 0件 | 6件 |
| 装置検出 | 不発 | 不発（前提の確認） |
| Guard 最長一致 | 11字「この時始めて気がついた」 | 8字「に沈んで行くその」 |
| 「百年」 | 1 | 0 |
| 「赤い日」 | 2 | 0 |
| 「数え」／「分らなく」 | 3 ／ 1 | 3 ／ 2 |
| 再生成 | 0回 | 1回 |

### 8.3 結果 — 語彙は剥がれたが、装置は残る

**減ったもの**は語彙レベルの借用だった。「百年」も結びの定型
「この時始めて気がついた」（第一夜）も消え、最長一致も下がった。

**残ったもの**は装置レベルの引き寄せである。

- 大人びた子供（第三夜）は健在。むしろ「次は右の松が消えます」と**予告する**
  ぶん全知性が強まった
- 赤い日の反復（第一夜・第七夜）は語が変わっただけで、「沈んでまた同じ赤さで
  昇る」構造は残った
- 計数して数えきれなくなる（第一夜の計数装置）は「三つ目まで」から
  「二十、三十、四十」へ**拡大**した

> **ブリッジの復旧は既視感を解かない。** 装置除外が狙っていた層は、
> ブリッジを足しても下がらなかった。

これで `device_exclusion` を自由創作でも on にする根拠が、n=1 の推測から
**同一 brief の対照**に上がった。§4 の「装置は続編でのみ汚染源」という前提は、
自由創作の観測1組と矛盾している。

### 8.4 次に測るときの注意

- **3本目（`device_exclusion: on`）は厳密な一変数にならない。** 除外は
  `assert_exclusions_hold` が合流点で効くため（§4.4）、ブリッジが運ぶ内容も
  同時に変わる。実測で `br_76de88e279c6` が計数カードの要約を通した記録がある。
  「装置除外 on」と「ブリッジの通す内容が変わる」が束になる
- **`device_exclusion` はプロファイル単位。** on にすると自由創作を含む
  全生成に効く。依頼ごとに切り替えたいならジョブ単位の設定が要る
- **設定値そのものを回帰テストで押さえること。** §8.1 の事故は、
  コードが正しくてもデータが戻れば防御が消えることを示した。期待値
  （`rules: assist` など）を固定するテストが無いと、次も生成物を読むまで
  気づけない（未着手）
