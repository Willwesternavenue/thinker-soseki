# thinkerllm への申し送り（thinker-soseki で見つかった不具合のうち、継承元に由来するもの）

2026-08-09 / 作成: thinker-soseki 側

このリポジトリは `7eedfa1`「初期コミット: thinkerllmのコードのみを複製（別人物モデル
検証用）」で thinkerllm から複製されている。以後の運用で見つかった不具合のうち、
**原因の行が複製時点で既に入っていたもの**を、向こうで調べられる形にして送る。

各項目は次の3点で構成する。

- **同じか**: thinkerllm でも症状が出るか（コード由来か、こちらの追加分か）
- **確かめ方**: 向こうで実行できる具体的な検査
- **直し方**: こちらで採った対処と、その根拠

⚠️ **こちらの修正をそのまま移植しないこと。** 判定側の実装が違えば妥当な対処も
変わる。「確かめ方」で症状の有無を先に確認してほしい。

## 1. `score` の意味が経路ごとに違うのに、同じ閾値で比較される

**場所**: `frontend/src/lib/rag/evidence.ts`

複製時点から、3つの経路が同じ `score` フィールドへ**意味の違う値**を入れている。

```ts
const strengthScore = { high: 1.0, medium: 0.8, low: 0.6 };
score: strengthScore[link.strength] ?? 0.7,   // 承認リンク: 結びつきの強さ
chunk.score = 0.5;                            // 全文検索: 固定値(PGroonga スコアは
                                              //   正規化されていないため捨てている)
score: (r.similarity as number) ?? 0.5,       // ベクトル検索: コサイン類似度
```

- **承認リンクの値**は「カードとその根拠の結びつきの強さ」であって、**目の前の質問との
  関連度ではない**
- **全文検索の 0.5** は関連度を何も表していない
- **コサイン類似度**だけが関連度である

**同じか**: 混在そのものは複製時点から存在する。ただし**症状が出るのは、この `score` を
閾値と比較して何かを判断している場合に限る**。当リポジトリでは「直接の原典があるか」の
判定（留保）で比較しており、そこで顕在化した。複製時点の `pipeline.ts` には
`abstention` / `hasDirectSource` / `MIN_DIRECT_SOURCE_SCORE` のいずれも無く、
`score` は**並べ替えにしか使われていなかった**（`sort((a,b) => b.score - a.score)`）。

したがって thinkerllm での確認事項は次の一点に絞られる。

> **`score` を閾値と比較している箇所が、その後 thinkerllm に追加されていないか。**

並べ替えだけなら実害は「承認リンクが常に上位に来る」に留まる（それ自体は意図とも
読める）。閾値比較が入った瞬間に、**承認リンクが1件でもあれば常に条件を満たす**という
形の誤判定になる。

**当リポジトリで実際に起きたこと**: 「森鴎外の作品について印象を述べて下さい」に対し、
コーパスに「鴎外」が0件であるにもかかわらず、無関係な資料が `score=0.8`（strength の
変換値）で「直接の原典」に数えられ、留保が発火しなかった。結果、**実在の人物についての
根拠の無い記述を、実在の人物の声で断定した**。

**確かめ方**:

```bash
# 1) score を閾値と比較している箇所があるか
grep -rn 'score.*[<>]=\?\s*0\.' frontend/src/lib/rag/ | grep -v test

# 2) あるなら、その判定に承認リンク由来が混ざるか
#    (fetchLinkedEvidence の戻り値が同じ配列に merge されているか)
grep -rn 'mergeEvidence\|fetchLinkedEvidence' frontend/src/lib/rag/
```

**直し方（当リポジトリの対処）**: 判定対象を `origin === "vector"` に限定した。
`EvidenceChunk.origin`（`"linked" | "vector" | "keyword"`）は複製時点から存在するので、
向こうでも同じ絞り込みが書けるはずである。

⚠️ **ただしこれだけでは足りなかった。** 実測で、分離したい2つが **0.002 差**だった。

| 質問 | ベクトル最高スコア | コーパス内の語の出現 | 留保すべきか |
|---|---|---|---|
| 森鴎外 | 0.443 | 「鴎外」0件 | **する** |
| 明治維新 | 0.445 | 「維新」17・「開化」32件 | しない |

閾値をどこに置いても分離できない。**コサイン類似度は「その語が原典に出てくるか」を
表していない**ため、別の信号（全文検索での在否）を判定に足す必要があった。
向こうで同種の判定を持つなら、**閾値の調整では解けない**ことを先に共有しておきたい。

## 2. 上位N件へ切り詰めてから並べ替えている

**場所**: `frontend/src/lib/rag/evidence.ts`（`diversifyEvidence` / `MAX_EVIDENCE = 10`）

複製時点から、`diversifyEvidence` が `MAX_EVIDENCE` 件へ切り詰める。当リポジトリでは
その後に「小説を作者の直接発言より後ろへ下げる」並べ替えを足したため、

```ts
rankByRoute(diversifyEvidence(merged), routeKind)   // ← 先に10件へ切られている
```

**並べ替えは「既に選ばれた10件の並び替え」しかできず、何を残すかに影響しない**という
状態になった。当リポジトリでは未修正（残課題）。

**同じか**: 切り詰めの位置は複製時点のまま。**thinkerllm でも、選抜後に順序へ意味を
持たせる処理を足していれば同じ形になる。**

**確かめ方**: `diversifyEvidence` の呼び出し前後に、優先度・重み付け・ロール別の
並べ替えが入っていないか。入っていれば、それは選抜に効いていない。

**直し方**: 未着手。順序を入れ替えるだけでは `diversifyEvidence` がスコア順ソートを
前提にしている点が崩れるため、多様性制御の挙動とセットで設計が要る。

## 3. judge の例外を「合格」として記録している

**場所**: `frontend/src/lib/rag/guard.ts`

複製時点の実装は、judge（軽量LLMによる出力検査）が例外で落ちたときも `pass: true` を
返し、trace には「合格」として記録していた。

**これが厄介なのは、失敗が失敗として見えないこと。** APIキー失効・モデルID変更・
レート制限で judge が**全件失敗しても、記録上は「全件 Guard 通過」に見える**。
検査が静かに死んでいることに気づく手段が無い。

**同じか**: **おそらく出る。** 当リポジトリ固有の条件は無い。

**確かめ方**:

```bash
grep -n 'catch' frontend/src/lib/rag/guard.ts
# catch の中で pass:true を返し、かつ「実行できなかった」ことを
# 呼び出し側へ伝える手段が無ければ同じ
```

**直し方（当リポジトリの対処、`fceab8e`）**: 戻り値に `executed: boolean` を足し、
trace では `pass` / `fail` / `skipped` の3値にした。**「合格」と「判定できなかった」を
混ぜない**のが要点。フェイルオープン（回答は止めない）自体は維持している。

## 4. 子プロセスへ親の環境変数をそのまま渡すと、値の意味が化ける

**場所**: `worker/src/main.py`（複製時点から）

```python
port = os.environ.get("PORT")
if port:
    _start_health_server(int(port))   # Cloud Run 上だと判断してヘルスサーバを立てる
```

当リポジトリで、画面からワーカーを起動する機能を足した際に踏んだ。Next.js の
dev server が持つ `PORT=5555` が `env: process.env` で子へ渡り、**ワーカーが
「Cloud Run がポートを指定した」と解釈**して bind に失敗、起動直後に落ちた。

```
OSError: [Errno 48] Address already in use
```

**同じか**: worker 側の `PORT` 解釈は複製時点から同じ。**向こうでワーカーを別プロセス
から spawn する経路があれば同じことが起きる。**

**確かめ方**: `PORT` を設定した状態で `python -m src.main` を起動して落ちるか。

**直し方**: 子へ渡す環境から `PORT` を落とす。一般形は
**「親にとっての意味」と「子にとっての意味」が違う変数を渡さない**こと。

⚠️ **この件で最も時間を無駄にしたのは `stdio: "ignore"` だった。** 起動失敗の理由が
どこにも残らず、画面には30秒後の「起動できませんでした」しか出なかった。原因の仮説を
3回立てて3回とも外した（PATH・秘匿キー・古いコード）。**出力をログへ落としてから
1回で分かった。** 子プロセスの出力を捨てないことを強く勧める。

## 5. フォーム保存で、入力欄の無い設定が消える（当リポジトリ由来。設計として共有）

**場所**: `frontend/src/app/admin/creative-profiles/profile.ts`（`034ace2`、当リポジトリ）

**同じか**: このファイルは向こうに無い。ただし**同じ形の設計は他にもありうる**ので
共有する。

JSON 列を持つ設定を、フォームの値だけで組み直して `update` で丸ごと置き換えていた。
フォームに入力欄が無いキーは、**保存のたびに既定値へ戻る**。エラーも警告も出ない。

実際に、Guard の閾値を1つ直しただけで別の設定が `assist` → `off` に戻り、
機能が黙って停止した。しかも**一度正しく設定したものが、正常な操作で後から壊れる**
形なので、「以前は動いていた」という記憶と食い違う。

**確かめ方**: JSON 列を `update` で置き換えている画面で、その JSON のキーが
すべてフォームに現れているか。1つでも欠けていれば同じ。

**直し方**: 既存値を読んでから、フォームが所有するキーだけを上書きする（置き換えでは
なく併合）。あわせて**期待値を固定する回帰テスト**を置いた。設定はデータなので、
コードのテストだけでは守れない。

## 併せて共有したい観察

上の5件のうち4件に共通する形がある。**安全装置や実行者が黙って効かなくなっても、
システムは正常に見え続ける。**

- judge が全件失敗しても「全件通過」に見える（#3）
- 留保が死んでも回答は返る。むしろ**自信のある回答が返る**（#1）
- ワーカーが不在でも画面は「準備中」と表示し続ける（#4）
- 設定が消えても機能は動き続ける（#5）

いずれも「エラーが出る」形で壊れない。**気づく唯一の方法が、出力を人が読むこと**に
なっている。向こうでも、検査・判定・実行の各層について
「これが黙って死んだとき、どこに痕跡が残るか」を一度棚卸しすることを勧めたい。

当リポジトリでは、状態の食い違いを機械的に洗う SQL を運用に組み込んでいる。

```sql
select 'thought_questions' t, status, count(*) from thought_questions group by 1,2
union all select 'thought_cards', status, count(*) from thought_cards group by 1,2
union all select 'judgment_rule_versions', status, count(*) from judgment_rule_versions group by 1,2
order by 1,2;
```

`where status = 'active'` で絞る RPC に対して実データが全部 draft、という食い違いが
典型的な形だった（代表質問113件が全て draft で、ルーターが常に空振りしていた）。
